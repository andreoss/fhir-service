= FHIR Service

A FHIR server. Resources are stored with every version of
themselves and answered over HTTP: read, write, history, search, bundles,
extended operations and long-running bulk jobs, under scoped authorization
and an audit trail. One store contract, three engines behind it, four
releases of the specification from one codebase.

== Build

[source,shell]
----
cargo build --workspace
cargo test --workspace
docker compose up -d --wait
cargo run --bin fhir-host
----

One binary in a minimal image: `docker build --file Containerfile .`. The
cluster template is in `deploy/`.

== Serving

[source,http]
----
GET  /health                  # the process and the engine behind it
GET  /metadata                # capability statement, generated from the routes
GET  /$versions               # the releases this instance serves
GET  /Patient?name=Smith&_count=10&_sort=-_lastUpdated
POST /                        # transaction and batch bundles
POST /Patient/1/$validate     # also $everything, $member-match, $docref
GET  /$export                 # submit a bulk job, then poll it by id
----

STU3, R4, R4B and R5 are served from one source: structure definitions and
the terminology catalogue are produced from the published artifacts by the
`models` tool and are never hand-edited.

Bearer tokens are verified against the keys their issuer publishes. Resource,
compartment and parameter scopes decide what a request may reach, and a job
answers only the caller that submitted it. Every read and every write leaves
a chained, verifiable audit record. Latency, count and failure are measured
per operation over a closed label set.

== Layout

`core` the model, its rules and the terminology, `contract` the storage
port and the suite every engine satisfies, `store` the query and index
types, `adapter-memory`, `adapter-relational` and `adapter-document` the
engines, `jobs` the durable queue and the bulk handlers, `telemetry` the
measurements, `api` the HTTP surface and the authorization, `host` the
binary.

`FHIR_BACKEND` chooses the engine, `FHIR_VERSION` the release,
`FHIR_DATABASE_URL` and `FHIR_DOCUMENT_URL` point the durable engines at
their servers, `FHIR_AUTH_ISSUER` names the issuer to trust.
